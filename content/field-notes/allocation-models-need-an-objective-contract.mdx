# allocation models need an objective contract

## two models, two questions

The inspected archived scripts derive allocation features from sample timing and receiving quantities, train a random-forest regressor to predict container counts, then aggregate predictions by machine.

The optimisation step uses those predicted counts as coefficients in a linear minimisation, constrains allocations to sum to the available total, and supplies a fixed list of hypothetical capacities.

Predicting a count does not establish what minimising that count as a cost should mean. The link between prediction and allocation is a modelling assumption, not something the solver can validate.

## boundaries still open

The feature builder expands receiving dates before a weekly merge and rounds allocations upward. Join multiplicity and conservation of the original total deserve explicit checks. The solver's fixed capacity list also assumes a particular number of machines.

A useful next step is a synthetic conservation fixture and a written objective with units: what exactly improves when the objective falls?

This is source-review-only, runtime-unverified. Archived code is not evidence of the current model's deployment or accuracy. Notebook outputs, datasets, and serialized models were not inspected.
