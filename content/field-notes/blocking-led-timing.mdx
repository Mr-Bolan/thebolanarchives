## what the code schedules

One sketch uses an input pull-up, waits for an active-low button press, delays for three
seconds, and flashes an LED ten times. It then waits until the button is released before
returning to the top of the loop.

The release wait prevents a held button from immediately retriggering the sequence. It
does not implement a timed debounce filter, and the flashing section does not inspect
the button. A brief press and release during that section is not remembered by this code.

A second sketch repeatedly blinks a fixed message using dot and dash durations. Its
lookup table covers only the characters used in that message, not a general text encoder.

## the useful limit

Both sketches make timing readable by putting delays next to output changes. The cost is
that the main loop cannot do other polling during those delays. That may be sufficient
for an isolated exercise; it becomes a constraint when another input needs attention.

A timestamp-driven state machine would be a possible next experiment, not an implemented
feature here. Hardware behavior, electrical debounce, and timing accuracy remain
unverified. This note records source structure, not a successful device test.
