## what exists

The server mounts route modules for several related record types and opens an existing
SQLite file in read-write mode. The inspected project and contact handlers use bound
query values for inserts, reads, updates, and deletes.

The interesting difference is in updates. The general project PATCH handler constructs
an update for every expected field, regardless of which fields the caller supplied.
The contact PATCH handler instead filters supplied keys through an allowlist and skips
null values. Separate project handlers also update individual fields.

A caller cannot infer one partial-update contract from the HTTP verb alone. Omitted
project fields still reach the database binding path; null contact fields cannot be used
to clear a value through the inspected handler. Exact missing-value behavior was not
tested against the driver.

## boundaries still missing

The inspected server configures a browser origin and request methods, but no
authentication middleware appears in that composition or the two reviewed route
modules. That is not evidence about any external deployment wrapper, and it is not a
claim that a live system is exposed.

Database error text is returned in responses, while list queries return whole rows.
Validation, response shaping, and a consistent update contract would be useful next
steps before using real records. This review did not open the database, run migrations,
start the server, or verify the frontend. It establishes a source prototype, not an
operational relationship-management system.
